# 架构、迁移与当前边界

## 组件

1. `server.py` / `controlplane`：Python 标准库 HTTP 服务与 SQLite 事务。接收多工具候选，按规范化 URL 去重，管理批次、租约、版本与审核。
2. `executors`：通过工具接口领取任务，独立安装 REA 与浏览器检查依赖；管理站点不导入 AI 或 REA 运行时。
3. `game-library`：独立 Git 仓库。每次可运行产出在 `games/<game-id>/versions/<version-id>/` 保留版本目录，关联提交 SHA。待验收代码也保存，是否公开由平台版本状态决定。
4. `data/artifacts`：原始资源包与运行产物。SQLite 保存它们的 ID、哈希与关联关系。试玩服务只读该目录。
5. `web`：中文管理界面。演示数据与真实 API 状态分开；演示模式不代表真实采集成果。

管理与试玩可用 `--service admin` 和 `--service play` 分别启动，使用相同 data-dir。当前虽使用不同端口、CSP 和 iframe sandbox，但仍是本机进程与共享存储，不是容器或操作系统级沙箱。

## 数据关系

候选内保留多条来源记录；候选可有多个处理任务；每个处理结果对应版本；版本关联 Git 提交和产物。一个游戏同时最多一个 published 版本。原版本重新发布可回滚，不修改原文件。

恢复/复刻过程属于执行工具；平台只校验租约、产物格式与阶段合法性。自动加载检查和人工玩法、画面、使用范围验收分开。不能把 report 中工具自报的成功当作独立证明。

## 迁移到公司 Git

- 游戏仓库与平台仓库分开，完整迁移 game-library 的 Git 历史和所有引用。
- 确认公司目标仓库为空后，用 Git mirror 流程迁移；不要对已有业务仓库直接执行 mirror push。
- 如将来采用 Git LFS，另迁移 LFS 对象；当前实现未自动配置 LFS。
- 公司部署配置 `--repo-dir` 指向新克隆路径、`--data-dir` 指向迁移数据；试玩地址与发布入口需同步更新。
- Git 不包含数据库、原始采集包和所有运行产物，单独迁移这些文件，否则预览和任务追溯不能恢复。

## 备份与恢复

推荐暂停派发、等待执行器停止并关闭管理及试玩进程，然后整体备份 data 和 game-library（包含 .git）。运行中备份 SQLite 需使用 SQLite backup API，不能只复制主数据库并忽略 WAL。凭证哈希保存在数据库，按敏感配置保护备份；环境里的 AI 密钥不进入仓库。

恢复到新目录后验证：候选数量、版本数量、Git 提交可读取、产物哈希一致、历史版本能试玩、未完成任务可重试。不要把旧进程和恢复进程同时指向不同拷贝后继续处理同一批次。

## 当前实现与生产扩展

已实现：本机平台、多个工具接入、资源包上传与限定下载、原子租约、阶段分流、源码版本 Git 记录、验收发布回滚、独立试玩、演示/真实模式。

内置执行器：REA 对提供的静态 JavaScript 源码进行真实分析与整理；浏览器加载检查；兼容模型 API 的玩法分析与代码生成通路。自有 fixture 可验证流程，不计入首批 30 款。

尚未代表已完成：30 款真实选品与复刻；任意 Web 游戏反编译；自动识别未知控件并自主通关；云端多租户鉴权；跨机器共享文件存储；对象存储大包上传；容器隔离；费用精确计量；自动定时采集。执行器已支持显式动作观察、截图反馈、运行失败后的有限次数 AI 修复和阶段时间/调用数限制；实际模型凭证未配置，真实模型生成质量尚未验证，具体边界以 executors/README.md 为准。

来源开关当前是平台配置记录，不会控制任意外部采集器；外部程序需自行遵循平台约定。源码提交和 SQLite 事务不是跨资源分布式事务，进程在 Git 提交后崩溃可能留下未关联版本目录；上线生产应增加协调日志和孤立产物对账。
