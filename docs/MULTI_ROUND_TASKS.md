# 多轮任务、版本与验收

任务中心默认按游戏显示当前未完成任务，历史执行和旧版本在详情里展开。已完成任务可通过“显示已完成”查看。

## 操作流程

1. 打开任务中心，点击“继续沟通 / 记录”。
2. 输入修改要求，点击“发送并继续处理”。执行器从上一版不可变快照续作，保留资源，修改应用代码。
3. AI 缺少信息时提交具体问题，任务进入“待回复”，释放执行租约。用户回复后恢复同一轮。
4. 修改通过浏览器验证后生成新版本，进入“待验收”。验证截图关联新版本。
5. 退回修复会保存意见，自动排入下一轮，不需要另建任务。旧版本进入“已被替代”，仍可查看和下载。
6. 功能验收确认玩法和画面后，版本为“已验收”、任务为“已完成”。资源使用信息保持原值；发布时单独核对。

队列和执行中的任务暂不接收另一轮修改，避免并发覆盖。任务完成本轮后可继续反馈。服务故障进入异常，缺信息进入待回复；两者分别展示。

## 接口

- 管理端 `POST /api/jobs/{id}/message`：`{"message":"用户回复或修改要求"}`。
- 执行器 `POST /api/v1/jobs/{id}/ask`：`{"lease_token":"当前租约","question":"具体问题"}`。提交成功后旧租约立即失效。
- 领取任务返回 `input.conversation`、`input.base_version` 和平台选定的源码快照路径。续作任务 `continuation=true`，阶段为 `reconstruct`，可由内置执行器领取。
- 续作产物提交 `changes`（路径到完整新文本的映射）、`entry`、`report` 和验证截图。服务端合并原快照，拒绝路径越界和覆盖资源目录。
- 验收 `POST /api/versions/{id}/approve` 需要 `checks.gameplay=true`、`checks.visual=true`。仅记录功能验收，不修改 `candidate.rights`。
- 发布仍要求版本已验收且使用范围为 `owned/licensed/open`。

## 保存与边界

对话存于 `messages`，轮次快照存于 `rounds`，历史版本和执行事件保留。启动迁移将已有被新版接替的退回任务与版本标记为已替代，不自动重跑游戏。部署前的数据库备份在 `data/backups/`。

续作当前支持不超过 500 个文件、256 MiB 的静态游戏包，修改不超过 100 个应用文本文件、2 MB；代码上下文上限为 220,000 字符。原资源与 vendor 目录保持不变；新增资源提取、工程依赖重构或超过此范围的任务仍需补充材料或单独适配，不会静默丢弃资源。

验证包含状态与租约测试、真实浏览器交互、功能验收按钮测试，以及使用本机 Codex 的独立续作实测。测试游戏使用临时数据库，不会替用户验收现有游戏。
