# 验收通过后自动供货

人工确认玩法、画面并通过验收后，在同一数据库事务内生成 `supply` 任务。独立后台线程自动检查、打包、提交、跟踪下游状态。下游失败不会回滚本地功能验收，旧的已验收版本不自动补发。

## 部署配置

在启动 `server.py` 的服务端环境配置以下变量，不要提交真实凭据：

也可运行 `tools/configure_supply.ps1`，以隐藏输入保存至仅当前用户/SYSTEM 可读的 `data/supply-config.json`。后台动态读取该文件，环境变量优先；可用 `SUPPLY_CONFIG_FILE` 指定独立配置文件。修改进程环境变量仍需重启服务。

| 变量 | 用途 |
|---|---|
| `SUPPLY_PLATFORM_BASE` | 下游 HTTPS 基址，不带路径和查询参数 |
| `SUPPLY_APP_ID` | 下游提供的 sup_ 开头 ID |
| `SUPPLY_APP_SECRET` | 下游提供的授权码 |
| `SUPPLY_ARCHIVE_DIR` | 对外静态文件主机对应的本机/挂载目录 |
| `SUPPLY_ARCHIVE_BASE_URL` | 该目录的 HTTPS URL 前缀 |
| `SUPPLY_EXPECTED_FINGERPRINT` | 从下游管理页核对的 12 位授权码指纹；首次提交及授权码变化时必须匹配 |

平台提交前自动执行签名向量自检、管理页指纹比对和 whoami 身份检查。工具服务配置表单已包含指纹；缺失或不匹配会阻断供货，不回滚功能验收。用户当前要求配置留空，因此真实提交尚未执行。

对平台内嵌源码转换产生的、具有完整资源映射和哈希证据的旧哈希文件，打包服务在独立临时副本中改为稳定语义名称并更新字面量引用，输出 supply-resource-map.json；原版本保持不变。无法证明映射关系的打包产物仍拒绝。静态检查不覆盖动态构造路径，仍依赖版本玩法测试及下游试运行。

分发目录仅存放经过本流程准备的供货 ZIP，不要暴露整个工作区、数据库或 Git 仓库。下游必须把下载域名加入供应方白名单，URL 直接 GET、不重定向，至少在提交下载期间保持有效。当前实现支持固定 HTTPS 静态目录，不负责部署公网服务或生成对象存储预签名 URL。保留文件，不自动清理已提交包。

配置后重启平台，在验收中心对之前因缺配置阻塞的任务点“重新检查 / 重试”。工作线程先调用 whoami 检查 app_id；离线签名实现使用官方 POST/GET 测试向量。正式首次交付仍须对照下游管理页核验授权码指纹并做双方联调。

可通过 `tools/check_supply.ps1 -Command online -Fingerprint <12位指纹>` 在不提交游戏的情况下验证指纹与身份，通过 `-Command probe-download` 验证本机到配置 HTTPS 下载地址的读取和 ZIP 摘要。后者仅写入无第三方游戏内容的样例包，不代表下游网络及白名单验证通过。当天操作清单见 `SUPPLY_SESSION_2026-10-22.md`。

## 交付者提供的版本报告

在现有产物/完成报告中增加 `report.supply`（不得伪造授权）。例如仅结构示意：

```json
{
  "supply": {
    "license_declaration": {
      "distributable": "yes",
      "owner": "经核实的实际权利人",
      "note": "授权依据及模板抽取、衍生作品发布范围"
    },
    "acceptance_steps": [
      {"action": "click", "target": "#start", "playing": true},
      {"action": "key", "value": "ArrowRight"}
    ],
    "known_limitations": ["经验证的实际限制"],
    "contact_note": "可选排障备注"
  }
}
```

上述 selector 和玩法步骤必须来自该版本实际验证，不应原样复制。验收步骤为下游运营参考，不自动替代人工验收。没有可分发授权时，游戏可以通过本地功能验收，但供货任务会阻塞。

旧报告缺少资料时，管理界面“补充供货资料”调用 `POST /api/supply/<version-id>/metadata`，body 为 `{"metadata": {...}}`。资料作为供货记录保存，不改写历史产物。已开始提交的任务不允许变更提交资料；网络失败可调用 `POST /api/supply/<version-id>/retry` 重试原提交。

## 包与状态

- 源目录取验收版本的 `source_directory`，生成独立 ZIP 到 `data/supply/`，拷贝到配置的分发目录；不改写原目录。
- 基础检查要求根目录 `index.html`，采用保守十进制 100MB/500MB 限制、2000 文件限制，拦截符号链接、路径穿越、常见执行脚本、构建源码、哈希命名和不支持的二进制引擎文件。
- 检查不等同于全面安全扫描、所有资源引用闭合或浏览器玩法验证。旧版本若仅包装一个外部服务链接或内嵌 ZIP，需要先整理运行工程并提交新版本。
- 稳定 ZIP 字节与摘要；一次提交绑定版本、submission_id、ZIP 摘要和请求内容摘要。超时/网络错误/5xx/429 保留同一编号重试；每次请求使用新 nonce。提交读超时 330 秒。
- 租约防止多个后台同时领取；进程重启后到期恢复。网络 I/O 不占 SQLite 事务。响应不存储原始请求 URL、签名或凭据。
- queued/received 每 300 秒，analyzing/building 每 60 秒，人工环节每 1800 秒；终态且问题同步完整后停止轮询。
- 下游 issues 按 revision/seq 增量合并，revision 变更清空旧清单，未知码按原 severity/title/suggestion 展示。
- 下游需要我方修改时，沿原任务交付新版本，再由人工验收触发新提交。接口没有替用户自动重跑、撤回或发布的逻辑。

## 验证

`tests/test_supply.py` 覆盖官方签名向量、验收入队、许可/配置阻塞、网络重试幂等、下游终态与问题、稳定打包、不支持产物、历史版本不补推以及界面资料恢复。全部使用隔离数据库/测试包和模拟下游；不使用真实游戏进行测试验收。
