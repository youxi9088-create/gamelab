# 互动玩法转换服务规范

版本：1.0 · 2026-10-23。面向服务维护者、接入项目和交付人员。

本文规定跨项目复用的流程和交付约定；标为“待实现”的接口与字段不是当前 API。已上线行为以代码及 [服务要求](SERVICE_REQUIREMENTS.md) 为准。引擎范围见 [适配流程手册](ENGINE_PLAYBOOKS.md)，接入步骤见 [项目接入指南](PROJECT_INTEGRATION.md)。

## 1. 服务目标与能力判断

接入项目提供游戏来源、可用材料、目标运行环境及需要复用的玩法，服务返回可追溯版本、实际验证结果和明确的二次开发范围。

适配单元由 **引擎及版本、运行包格式、宿主依赖、验证条件** 共同确定。网站名、游戏名、曾有一个成功案例，都不能单独证明支持新输入。识别到引擎只代表可以选择处理路径。

每项交付分别声明以下能力，不能用一个“转换成功”替代：

| 交付能力 | 必须提供的依据 | 适合下游做什么 |
|---|---|---|
| 可独立运行 | 实际运行、资源及依赖检查、代表性玩法证据 | 嵌入或部署现有玩法 |
| 业务逻辑可修改 | 明确的文件、修改入口、依赖和验证方法 | 调整规则、数值、流程或表现 |
| 模块已验证可复用 | 模块输入输出、独立夹具、脱离原游戏后的验证记录 | 移植到另一互动玩法 |

每个模块还须标记“已验证可复用／需拆解适配／仅运行包／未确认”。页面代码可修改不代表 WASM、SWF 核心可修改；有 JavaScript 文件也不代表已拆出独立业务模块。

## 2. 统一流程与阶段退出条件

引擎适配器负责差异步骤；排队、租约、证据、版本、用量、验收和交付使用共享服务。自动转换、续作、本地导入和外部执行器不能各自定义成功标准。

| 节点 | 工作内容 | 退出依据 | 未满足时 |
|---|---|---|---|
| identify | 确认实际入口、来源类型及运行特征 | 入口证据及可解释的路径选择 | 保留候选入口，说明缺什么 |
| acquire | 获取代码、运行包与已声明资源 | 来源、文件清单、哈希、获取失败项 | 补齐可取得资源，否则阻断 |
| analysis | 分析依赖、可编辑性、宿主及验证方案 | 所选适配范围和未支持依赖 | AI 分析证据或请求材料 |
| adapt | 执行适配，保留原材料 | 新产物、修改记录和哈希 | 有限修复或明确阻断 |
| test | 验证启动、输入、代表性闭环、继续及适用存档 | 绑定当前版本的真实检查结果 | 保存草稿，补剩余检查 |
| repair | 分析实际失败，修改允许修改的内容并复验 | 复验通过才返回原失败节点推进 | 预算耗尽或无能力时保留阻断 |
| delivery | 保存版本、报告及证据 | 不可变版本和交付范围完整 | 草稿不视为完成 |
| review | 人工确认玩法与画面 | 明确的验收记录 | 退回同任务续作 |
| publish | 执行发布或下游供货 | 各自的发布／供货结果 | 不回滚已经成立的功能验收 |

repair 是条件分支，不是每个游戏必做步骤；修复记录必须保留原失败阶段。新版本修改后要重新验证受影响部分，不能沿用修改前结论。代表性闭环不要求无限通关，未访问内容写入覆盖边界。

## 3. 状态、续作与完成定义

- 任务、阶段、版本、批次、发布和供货是不同状态，不得合并为一个布尔值。
- `queued` 表示排队；`running` 表示占用执行租约；`review` 表示等待人工验收；`completed` 表示任务已验收。不能把 `review` 当作已批准发布。
- `blocked/failed/waiting_input` 保留原因及下一步；阶段 `succeeded` 只证明该阶段的实际覆盖范围。
- 阶段展示使用共享 `pipeline.presentation`，区分本轮完成、历史完成、结果未确认、未触发修复、未发布。进度不能由心跳次数或固定 90% 推算。
- 续作使用同一任务和明确的基线版本，生成新轮次、新版本，不覆盖历史产物。旧证据只有在材料及适用条件一致时才能引用。
- 产物可续作不代表浏览器游戏状态可恢复。没有运行存档时须说明必要回放；不能声称直接恢复到旧画面。
- 当前全局同时执行一个转换任务。后续项目接入也必须进入共享队列，不得另起执行器绕过领取事务限制。

## 4. AI 与故障处理规范

本地 Codex 桥接与 API 调用使用相同的证据、工具权限、结果判定和账本。AI 提出假设及行动，执行器实际执行并保存反馈。

排查顺序：读取具体失败 → 检查已有材料 → 形成可验证假设 → 在权限内处理 → 重新检查 → 继续或说明阻断。不能仅根据模型文字改为成功。

| 问题类别 | 规范处理 |
|---|---|
| 模型或网络临时中断、限流 | 保存已验证检查点，按预算和服务状态恢复；不把中断算作玩法失败 |
| 入口被延迟页面遮挡 | 使用已有明确启动／跳过广告契约，记录实际等待与点击 |
| 原始资源缺失 | 按已记录来源有限补齐；原站不存在时明确列出缺项 |
| 宿主接口不兼容 | 仅修改本轮允许修改的宿主，失败回退，再验证 |
| 未支持引擎或运行契约 | 分析入口；没有可执行方案时输出能力缺口，不无限重试 |
| 账号、后端、支付、广告依赖 | 声明实际影响；不伪造认证、奖励或服务器结果 |
| 玩法或存档证据不足 | 针对缺项继续观察，已有闭环不重复从头验证 |

当前修复有轮次、时间、调用和无进展上限。新适配器必须遵循这些限制；具体有效值取部署配置及对应执行路径，不能复制旧文档中的数字作为客户端重试策略。

## 5. 统一交付清单

以下是交付语义约定；现有文件名和字段可能分布在版本报告、执行证据和目录索引中，尚未统一为单一 manifest API。

1. **身份与来源**：任务、轮次、不可变版本、来源入口、原始材料哈希、实际采用的适配方案。
2. **运行产物**：入口、文件清单、依赖、运行环境、展示尺寸、输入方式、部署说明。
3. **游戏规格说明书**：玩法、操作、循环、内容范围、进度、存档；未知项明确标注。
4. **二次开发说明**：可修改文件与逻辑、模块接口、初始化／销毁方式、宿主耦合、移植步骤及上述复用级别。
5. **验证证据**：实际动作、截图、结果、错误、存档恢复检查；明确未验证范围和所用基线。
6. **限制与归属**：离线能力、缺少的在线功能、资源使用信息及发布条件。功能验收与资源使用记录分别保存。
7. **资源账本**：AI 模式、调用、实际用量、费用及未知项；不得把排队或人工等待计入执行耗时。

新游戏交付至少说明“能改哪里、能搬走什么、依赖什么、验证到哪里”。如果接入方目标是提取玩法模块，只有运行包成功不能满足该目标。

## 6. 新增适配能力的准入

1. 用 [适配流程手册](ENGINE_PLAYBOOKS.md) 的模板登记精确输入特征、依赖和排除条件。
2. 识别依据来自文件和运行证据，不能增加按游戏名称、ID、截图路径判断的分支。
3. 实现置于共享执行层，声明其调用路径；通过相同交付检查进入版本库。
4. 用自有夹具及隔离数据库覆盖识别正反例、缺资源、宿主失败、修复失败回退、续作与报告边界；需要截图时查看实际渲染。
5. 技术夹具通过、真实案例通过、跨案例可复用分别登记。正式游戏只执行用户授权的交付任务，不用于开发回归。
6. 按 Git 提交发布，记录适配规则变化；受影响版本保留原产物，不批量覆写或自动重跑。
7. 将新故障的触发条件、证据、处理办法、适用范围写回手册，并补隔离夹具，供下一项目复用。

## 7. 跨项目产品化的实现顺序

当前已具备共享执行器、多个运行契约、受限 AI 修复、不可变版本和项目内角色。以下仍需实现，不能向其他项目承诺已提供：

| 优先级 | 建设项 | 完成判据 |
|---|---|---|
| P0 | 项目调用凭证及作用域 | 项目服务端可提交、查询、续作、下载；不能访问别的项目或管理凭据 |
| P0 | 版本化能力发现及预检接口 | 返回适配范围、材料缺项、复用级别和机器可判定的原因；预检通过不等于转换通过 |
| P0 | 项目任务接口与结构化结果 | 幂等提交、按任务查询、分页事件、统一交付清单；接入方无需读取全站 state |
| P1 | 适配器统一注册 | 当前分散的运行契约与注册配置汇入同一能力目录，文档和运行时来源一致 |
| P1 | 版本化错误及恢复协议 | 返回原失败节点、错误类别、是否可重试、下一动作和基线版本 |
| P1 | SDK、接入示例和隔离契约测试 | 新项目用自有样例完成提交到获取结果，校验超时重试不重复建任务 |
| P2 | 完成通知和独立额度 | 按项目计量；如提供回调，签名、幂等、重试和补查均有实现与测试 |

当前同一部署内数据项目内共享。如果不同项目需要数据隔离，应先补权限和存储隔离；在此之前只能共享同一数据范围或独立部署。不得仅添加 project_id 字段就宣称已经多租户隔离。
